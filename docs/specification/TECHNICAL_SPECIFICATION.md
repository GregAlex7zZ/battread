# Data Standardization Library
## Technical Specification v0.1

**Status:** Draft  
**Specification version:** 0.1  
**Target implementation:** Python  
**Primary public tabular interface:** pandas  
**Recommended interchange format:** Apache Parquet  
**Primary audience:** Electrochemistry and battery research community

---

# 1. Purpose

The purpose of this project is to provide a reliable, extensible, vendor-independent data ingestion and standardization layer for electrochemical cycling data.

The library shall read data originating from different battery cyclers and generic tabular files, extract the minimum set of measurements required by downstream applications, normalize their representation, optionally concatenate sequential acquisitions, and export the result using a stable canonical schema.

The library is intentionally **not** an electrochemical analysis package.

Its primary responsibility is:

> Convert heterogeneous electrochemical cycling data into a minimal, predictable, vendor-independent representation suitable for subsequent analysis.

The canonical standardized output consists of exactly:

```text
time_s
current_mA
voltage_V
```

The library is intended primarily for researchers working with electrochemical and battery cycling data, while remaining suitable for use as a general Python dependency in other scientific software.

---

# 2. Target users

The initial users are expected to be:

- researchers working with battery cyclers;
- electrochemists working with data from multiple instrument vendors;
- research laboratories requiring a common preprocessing workflow;
- developers building electrochemical analysis software on top of standardized datasets.

The project should remain approachable for scientific users with basic Python knowledge while exposing sufficiently explicit behavior for developers.

# 5. Functional responsibilities

The library shall provide functionality for:

- automatic file-format detection;
- vendor-specific data reading;
- generic CSV/TXT reading;
- automatic column recognition;
- unit recognition;
- unit conversion;
- elapsed-time normalization;
- current extraction;
- current reconstruction from capacity information where scientifically justified;
- validation of standardized data;
- concatenation of sequential datasets;
- chunk-based processing where possible;
- export to supported standardized formats.

# 6. Explicit non-goals

The following functionality is intentionally outside the scope of this library:

- cycle detection;
- half-cycle detection;
- step detection;
- electrochemical charge/discharge classification;
- capacity calculation for analytical purposes;
- energy calculation;
- Coulombic efficiency;
- energy efficiency;
- state-of-charge estimation;
- state-of-health estimation;
- C-rate calculation;
- degradation analysis;
- smoothing;
- filtering;
- interpolation;
- outlier removal;
- resampling;
- plotting;
- scientific visualization;
- electrochemical interpretation.

These operations belong to a separate downstream analysis library.

The separation between the two projects shall remain explicit.

# 7. Architectural boundary with downstream analysis

The intended workflow is:

```text
PROPRIETARY / GENERIC DATA
           │
           ▼
STANDARDIZATION LIBRARY
           │
           ▼
STANDARDIZED DATA FILE
           │
           ▼
DOWNSTREAM ANALYSIS LIBRARY
           │
           ▼
GUI / VISUALIZATION / ANALYSIS
```

The downstream analysis library shall be capable of consuming the standardized output without importing this library.

A file-based standardized interface is preferred in order to maintain a strong architectural and licensing boundary between projects.

# 8. Design principles

## 8.1 Scientific conservatism

The library may automatically change the **representation** of a measurement.

It shall not silently change its scientific meaning.

Acceptable automatic transformations include:

```text
A → mA
mV → V
ms → s
"Time/s" → time_s
"Ewe/V" → voltage_V
```

Operations such as the following shall not occur automatically:

```text
smoothing
interpolation
outlier removal
resampling
automatic row deletion
scientific interpretation of current direction
voltage correction
arbitrary missing-value filling
```

---

## 8.2 Predictability over cleverness

When the library cannot determine an interpretation safely, it shall prefer an explicit error to an unsupported guess.

A false negative is preferable to a silent false positive when the false positive could change the scientific interpretation of the dataset.

---

## 8.3 Minimal canonical representation

The standardized output shall contain only the information required by downstream software.

Version 0.1 therefore defines only:

```text
time_s
current_mA
voltage_V
```

Other source columns may temporarily participate in the conversion pipeline but shall not be retained in canonical output.

---

## 8.4 Vendor independence

Equivalent physical measurements shall result in equivalent standardized output regardless of the original instrument vendor.

Downstream software shall not require knowledge of whether data originated from Bio-Logic, Neware, CSV, TXT, or another future reader.

---

## 8.5 Modularity

Vendor-specific functionality shall be isolated from generic functionality.

Adding a new reader shall not require substantial modifications to unrelated readers.

Column recognition, unit handling, validation, merging, and exporting shall remain generic wherever possible.

---

## 8.6 Large-data awareness

The architecture shall not assume that complete source files or standardized datasets fit comfortably in RAM.

Individual files may reach several gigabytes.

Chunk-based and streaming-oriented processing shall therefore be supported wherever technically possible.

---

# 9. Normative terminology

The keywords **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** indicate requirement strength.

- **MUST / MUST NOT** define required behavior.
- **SHOULD / SHOULD NOT** define strongly recommended behavior.
- **MAY** defines optional behavior.

# 10. Canonical standardized schema

Every successfully standardized dataset MUST contain exactly the following canonical measurement columns:

```text
time_s
current_mA
voltage_V
```

The canonical column order MUST be:

1. `time_s`
2. `current_mA`
3. `voltage_V`

The definitions are:

| Column | dtype | Unit | Meaning |
|---|---|---|---|
| `time_s` | `float64` | s | Elapsed time from the beginning of the standardized dataset |
| `current_mA` | `float64` | mA | Directly measured or safely reconstructed current |
| `voltage_V` | `float64` | V | Measured electrochemical voltage |

All canonical columns MUST use `float64` by default.

Lower-precision output MAY be supported in the future as an explicit user choice but SHALL NOT replace `float64` as the reference representation.

## 10.1 Valid canonical datasets

A complete canonical dataset MUST be nonempty and contain at least one finite time value. Reading, writing, or merging an empty dataset or a dataset with no finite time MUST raise `IncompatibleDataError`; `is_standardized()` MUST return `False` for such datasets.

`NaN` values MUST be preserved and reported as specified in Section 55. Positive or negative infinity in any canonical column MUST raise `IncompatibleDataError`; infinity MUST NOT be retained as a canonical measurement.

---

# 11. Canonical output metadata

Version 0.1 does not require metadata to be retained.

Information such as:

```text
source filename
instrument vendor
instrument serial number
software version
test start time
original column names
file hash
```

shall not be part of the standard output unless a future specification introduces an optional metadata mechanism.

A future optional provenance column MAY be considered without changing the canonical measurement schema.

# 12. Time semantics

## 12.1 Canonical unit

Time MUST be represented in seconds.

Canonical column:

```text
time_s
```

---

## 12.2 Initial time

The first finite time of every independently standardized dataset MUST be:

```text
time_s = 0
```

The first finite source time MUST define the new origin. Leading rows with missing time MUST remain present with `NaN` time.

Conceptually:

```text
standard_time = source_time - first_finite_source_time
```

Processing chunks share the origin of the entire logical dataset; each chunk MUST NOT be independently shifted to zero.

---

## 12.3 Supported time representations

Readers SHOULD recognize, where unambiguous:

```text
seconds
milliseconds
microseconds
minutes
hours
days
HH:MM:SS
HH:MM:SS.sss
absolute timestamps
elapsed timestamps
```

Absolute timestamps MAY be converted to elapsed time when their interpretation is reliable.

---

## 12.4 Time monotonicity

Within a single dataset, valid finite time values MUST be monotonically non-decreasing.

This comparison MUST continue across missing rows; for example, `[0, NaN, 2, NaN, 1]` is invalid.

Example of valid data:

```text
0
1
2
2
3
4
```

Duplicate timestamps may therefore be preserved.

The following is invalid:

```text
0
1
2
1.5
3
```

When time moves backwards, the operation MUST stop.

The library MUST NOT attempt to repair non-monotonic time automatically.

A dedicated exception SHOULD be provided:

```python
NonMonotonicTimeError
```

---

## 12.5 Missing time values

Rows containing missing time values MUST NOT be silently removed.

Their existence MUST produce a warning.

Operations requiring unambiguous temporal ordering MAY fail if missing values make safe processing impossible.

---

# 13. Current semantics

## 13.1 Canonical unit

Current MUST be represented in milliamperes.

Canonical column:

```text
current_mA
```

---

## 13.2 Direct current precedence

When a usable current column exists in the source, it MUST take precedence over any reconstructed current.

The library MUST NOT replace existing valid source current with an estimate derived from capacity.

## 13.2.1 Usable direct current

A direct current column is usable when its measured-current semantics, compatible unit, and numeric compatibility are established. Usability MUST NOT depend on the count of finite current values observed in a sample or processing chunk.

When selected direct current contains `NaN` values, including a present column whose values are all `NaN`, those values MUST be retained with a warning. The library MUST NOT replace the column or fill individual missing direct-current values from capacity. Infinity MUST fail canonical validation rather than trigger capacity fallback.

An invalid explicit current mapping or unsupported unit MUST raise an appropriate domain exception instead of silently falling back to reconstruction.

---

## 13.3 Current sign

When current is read directly from a source file, its original sign MUST be preserved.

The standardization library shall not automatically reinterpret current according to charge or discharge.

For example, if a source vendor represents charging current as negative, that sign remains negative in standardized output.

Interpretation of current direction belongs to downstream analysis.

---

## 13.4 Supported current units

The recognition and unit-conversion systems SHOULD support at least:

```text
A
mA
µA
μA
uA
nA
```

All values shall ultimately be converted to `mA`.

---

# 14. Voltage semantics

## 14.1 Canonical unit

Voltage MUST be represented in volts.

Canonical column:

```text
voltage_V
```

---

## 14.2 Supported voltage units

The recognition system SHOULD support at least:

```text
V
mV
µV
μV
uV
```

---

## 14.3 Measurement versus control values

When multiple voltage-related columns exist, actual measured voltage SHALL be preferred over quantities such as:

```text
voltage setpoint
voltage limit
voltage range
control voltage
target voltage
programmed voltage
```

when enough evidence exists to distinguish them.

---

# 15. Automatic column recognition

Automatic column recognition is a core subsystem of the project.

It MUST be independently testable and extensible.

It SHOULD NOT be implemented as scattered vendor-specific `if/else` logic.

The recognition engine shall attempt to identify at least:

```text
time
current
voltage
capacity
delta_capacity
charge_capacity
discharge_capacity
```

Only time, current, and voltage are retained in canonical output.

Capacity-related quantities may be used internally for current reconstruction.

---

# 16. Recognition philosophy

Column recognition shall follow:

> Search broadly, classify carefully, decide conservatively.

The recognizer SHOULD understand a large variety of:

- vendor-specific names;
- historical names;
- abbreviations;
- capitalization styles;
- unit formatting styles;
- punctuation styles;
- user-generated column labels.

However, genuinely ambiguous matches MUST NOT be silently resolved arbitrarily.

---

# 17. Header normalization

Before semantic matching, labels SHOULD undergo normalization.

Normalization MAY include:

- Unicode normalization;
- case folding;
- whitespace normalization;
- punctuation normalization;
- bracket normalization;
- slash normalization;
- separation of quantity and unit;
- normalization of micro symbols;
- removal of redundant whitespace;
- normalization of common scientific notation.

For recognition purposes, labels such as:

```text
Current(mA)
Current / mA
current [mA]
I/mA
I (mA)
```

may therefore be considered related.

---

# 18. Alias registry

Known aliases SHOULD be maintained in a centralized, declarative registry.

Conceptually:

```text
time:
    exact aliases
    token aliases
    regex patterns
    compatible units
    incompatible terms

current:
    ...

voltage:
    ...

capacity:
    ...
```

The alias registry SHOULD be easily extensible without changing the central recognition algorithm.

Vendor-specific aliases MAY be added by individual readers.

Generic aliases SHOULD remain shared.

---

# 19. Recognition evidence

Candidate identification MAY use multiple independent forms of evidence:

- normalized column name;
- exact alias matching;
- known manufacturer-specific aliases;
- semantic token matching;
- regular-expression matching;
- recognized units;
- file-format knowledge;
- data type;
- numeric content;
- expected numerical behavior;
- negative keywords;
- user-provided hints.

No single heuristic is required to make a decision in isolation.

---

# 20. Negative recognition evidence

The recognition engine MUST distinguish physical measurement columns from similarly named auxiliary fields whenever sufficient evidence exists.

Examples:

```text
Current(mA)       → likely current

Current Range     → not current
Current Limit     → not current
Current Setpoint  → not preferred current
Current Density   → not ordinary current
```

Equivalent safeguards SHOULD exist for voltage, time, and capacity.

---

# 21. Recognition confidence and ambiguity

The implementation SHOULD internally represent recognition confidence.

The exact scoring system is an implementation detail.

The normative behavior is:

### One clearly superior candidate

Select automatically.

### Several candidates with one clearly superior candidate

Select automatically.

### Several genuinely plausible candidates

Stop and raise an ambiguity error.

### No usable candidate

Follow the defined fallback behavior for that quantity.

An ambiguity error SHOULD list the columns that produced the ambiguity.

Example:

```text
Ambiguous current columns detected:

- "Current"
- "Cell Current"

Automatic selection cannot be performed safely.
Provide an explicit column mapping.
```

---

# 22. Explicit column mapping

Automatic recognition MUST always have an explicit override.

Users MUST be able to specify columns by name.

Example:

```python
read(
    "file.csv",
    columns={
        "time": "Elapsed Time",
        "current": "Cell Current",
        "voltage": "Potential",
    },
)
```

Users MUST also be able to specify columns by positional index.

Example:

```python
read(
    "file.txt",
    columns={
        "time": 0,
        "current": 4,
        "voltage": 7,
    },
)
```

Explicit user mappings MUST take precedence over automatic recognition.

---

# 23. Unit recognition

Quantity recognition and unit recognition are separate concerns.

For example:

```text
Current
```

may establish the quantity while not establishing whether the values are expressed in:

```text
A
mA
µA
```

The unit system MUST therefore be independently capable of:

- extracting units from headers;
- receiving units from vendor-specific readers;
- receiving explicit user overrides;
- validating compatibility between quantity and unit.

---

# 24. Explicit unit mapping

When units cannot be determined reliably, users SHOULD be able to provide explicit units.

Example:

```python
read(
    "file.txt",
    columns={
        "time": 0,
        "current": 1,
        "voltage": 2,
    },
    units={
        "time": "s",
        "current": "mA",
        "voltage": "V",
    },
)
```

Explicit units MUST override automatic unit inference.

The library MUST NOT silently perform a scientifically significant conversion based on an unsupported unit guess.

---

# 25. Capacity recognition

Capacity is not part of canonical v0.1 output.

Capacity-related fields are auxiliary source information.

They MAY be read temporarily when required to reconstruct current.

Capacity recognition shall follow:

> Search broadly, classify carefully, reconstruct only when semantics are sufficiently established.

Numeric behavior alone MUST NOT establish the physical meaning of a capacity column.

---

# 26. Capacity semantic classes

The recognition subsystem SHOULD classify capacity candidates into the following semantic categories where sufficient evidence exists.

```text
cumulative_signed
delta_signed
charge_capacity
discharge_capacity
generic_capacity
unknown_capacity
```

---

## 26.1 `cumulative_signed`

A signed cumulative charge-transfer quantity.

Current MAY be reconstructed from its derivative.

---

## 26.2 `delta_signed`

A signed charge increment associated with an individual sampling interval.

Current MAY be reconstructed using the interval charge directly.

---

## 26.3 `charge_capacity`

A cumulative quantity explicitly representing charge capacity.

Its increasing derivative corresponds to positive reconstructed current.

---

## 26.4 `discharge_capacity`

A cumulative quantity explicitly representing discharge capacity.

Its increasing derivative corresponds to negative reconstructed current.

---

## 26.5 `generic_capacity`

The column is confidently recognized as some type of capacity, but its exact semantics cannot be established.

Possible names include:

```text
Capacity
Cap
Q
```

without additional information.

A `generic_capacity` field MUST NOT automatically be used for current reconstruction.

---

## 26.6 `unknown_capacity`

The field appears capacity-like but neither its quantity nor semantics can be established confidently.

It MUST NOT be used automatically.

---

# 27. Capacity recognition evidence hierarchy

Capacity classification SHOULD use the following evidence hierarchy.

## 27.1 Format-specific reader knowledge

The strongest evidence comes from readers that understand a source field's semantics.

Examples include:

- known binary field identifiers;
- known vendor-specific textual columns;
- documented format-specific quantity semantics.

---

## 27.2 Explicit semantic names

Headers such as:

```text
Charge Capacity
Discharge Capacity
Charge Capacity (mAh)
Discharge Capacity (Ah)
Delta Capacity
dq/mA.h
```

provide strong semantic evidence.

---

## 27.3 Quantity and unit combination

Recognized capacity names combined with compatible physical units increase confidence.

---

## 27.4 Numerical behavior

Data behavior MAY validate or reject an interpretation.

Examples include:

- monotonic increase;
- negative changes;
- resets;
- constant regions;
- non-finite values;
- discontinuities.

Numerical behavior SHOULD NOT independently determine semantics when multiple scientifically plausible interpretations remain.

---

## 27.5 Explicit user declaration

The user MAY explicitly define the capacity interpretation.

Conceptually:

```python
read(
    "file.csv",
    columns={
        "time": "Time",
        "voltage": "Voltage",
        "capacity": "Capacity",
    },
    capacity_kind="cumulative_signed",
)
```

Exact API naming shall be defined in the Public API Specification.

---

# 28. Capacity units

Capacity recognition SHOULD support at least:

```text
Ah
mAh
µAh
μAh
uAh
C
```

Internally, capacity used for current reconstruction SHOULD be converted to a known common unit before differentiation.

For formulas expressed in this specification, `mAh` is used as the reference charge unit.

# 29. Current acquisition priority

Current shall be obtained according to the following priority:

```text
direct usable current
        │
        ▼
explicit user-provided capacity semantics
for an explicitly selected capacity column
        │
        ▼
automatic capacity-based reconstruction
with sufficiently known semantics
        │
        ▼
failure
```

Usable direct source current ALWAYS takes precedence.

An explicit capacity selection MUST NOT be silently replaced by a different reconstruction strategy if its unit, alignment, interval, or reset safety checks fail.

---

# 30. Current reconstruction from cumulative signed capacity

For cumulative signed capacity represented in `mAh`:

\[
I_i[\mathrm{mA}]
=
3600
\frac{Q_i-Q_{i-1}}
{t_i-t_{i-1}}
\]

where time is represented in seconds.

Conceptually:

```text
I = ΔQ / Δt × 3600
```

The sign of reconstructed current follows the sign of `ΔQ`.

An explicit generic `capacity_kind="cumulative_signed"` declaration asserts that the selected field is continuous signed charge transfer with no unknown resets. Negative increments are legitimate discharge and MUST NOT independently be diagnosed as resets.

The interval is always the preceding interval between adjacent original rows. When cumulative reconstruction is selected, supplying a non-`None` `capacity_interval` MUST raise `CurrentReconstructionError` rather than silently ignoring it.

---

# 31. Current reconstruction from incremental capacity

Where a field represents signed charge transferred during an interval:

\[
I_i[\mathrm{mA}]
=
3600
\frac{dQ_i[\mathrm{mAh}]}
{dt_i[\mathrm{s}]}
\]

The alignment between `dQ` and the corresponding time interval MUST follow the known semantics of the source field.

It MUST NOT be assumed generically.

## 31.1 Incremental-capacity alignment

For `delta_signed`, alignment MUST be established by a reader hint or the explicit `capacity_interval` option. The explicit option MUST take precedence over a reader hint. Missing alignment MUST raise `CurrentReconstructionError`, even when `capacity_kind="delta_signed"` is supplied.

| `capacity_interval` | Meaning of `dQ_i` | Time interval | Unavailable endpoint |
|---|---|---|---|
| `"previous"` | Charge transferred during `(t[i-1], t[i]]` | `t[i] - t[i-1]` | First current is `NaN` |
| `"next"` | Charge transferred during `[t[i], t[i+1])` | `t[i+1] - t[i]` | Last current is `NaN`; first may be finite |

Intervals refer to adjacent original rows, including across processing chunk boundaries. `capacity_interval` applies only to incremental reconstruction; a non-`None` value MUST raise `CurrentReconstructionError` when cumulative reconstruction is selected.

---

# 32. Separate charge and discharge capacities

When both cumulative charge capacity and cumulative discharge capacity are available and their meanings are reliable:

\[
I[\mathrm{mA}]
=
3600
\frac{
\Delta Q_{\mathrm{charge}}
-
\Delta Q_{\mathrm{discharge}}
}
{\Delta t}
\]

Therefore reconstructed current follows:

```text
charge     → positive
discharge  → negative
```

This convention applies only to reconstructed current.

Directly measured source current retains its original sign.

Both cumulative charge and discharge capacity MUST be non-decreasing within their declared continuous semantics. A decrease MUST raise `CurrentReconstructionError`; it MUST NOT become a negative derivative masquerading as current. A reader MAY instead select a documented, tested reset-free source field, but MUST NOT unwrap or repair capacity resets in v0.1.

---

# 33. Single-sided capacity information

## 33.1 Charge capacity only

Charge capacity alone MAY be used only where source semantics establish that the relevant data corresponds to charge intervals.

The library MUST NOT assume that absent discharge capacity means zero discharge current across a mixed dataset.

## 33.2 Discharge capacity only

Equivalent restrictions apply to discharge-only capacity.

---

# 34. Ambiguous capacity

If:

- direct current is unavailable;
- a capacity-like field exists;
- its semantics cannot be established safely;

the library MUST stop automatic reconstruction.

It SHOULD produce an actionable error.

Example:

```text
Current is not available.

A possible capacity column was found:

    "Capacity (mAh)"

Its semantics cannot be determined safely.

Provide an explicit capacity interpretation or column mapping.
```

---

# 35. Capacity discontinuities

Unexpected resets or discontinuities MUST NOT be silently repaired.

For example:

```text
0.0
0.5
1.0
1.5
0.0
0.4
```

shall not automatically be interpreted as:

- a cycle boundary;
- a half-cycle boundary;
- an instrument restart;
- a valid capacity reset.

## 35.1 Reset evidence

A negative increment or a large change in cumulative signed capacity MUST NOT alone establish a reset or discontinuity. Signed capacity can legitimately decrease during discharge. The example above therefore does not, by itself, prove a reset in a declared continuous signed field.

When capacity reconstruction is selected, independently known reset markers or a violation of documented source semantics in the selected capacity MUST raise `CurrentReconstructionError`. Version 0.1 MUST NOT unwrap or repair such resets, including through vendor-specific reconstruction.

Generic heuristic repair is outside v0.1.

---

# 36. Invalid reconstruction intervals

Current reconstruction requires a valid positive time interval:

```text
Δt > 0
```

Zero, negative, missing, or invalid intervals MUST NOT result in silent division by zero or infinite current.

For zero, missing, or otherwise invalid reconstruction intervals, affected current values MUST become `NaN`, and their original rows MUST be retained. A negative finite time interval MUST instead raise `NonMonotonicTimeError` under Section 12.4; canonical infinity MUST fail validation under Section 10.1.

A warning MUST be emitted.

## 36.1 Missing rows and global failure

Reconstruction MUST use adjacent original rows only. It MUST NOT differentiate across a missing time or capacity row by joining surrounding valid rows.

If the complete reconstruction yields no finite current value, the operation MUST raise `CurrentReconstructionError`. Unavailable endpoint samples described in Section 37 are valid only when at least one other reconstructed current is finite. Known semantic violations MUST fail as specified in Section 35 even if other reconstructed samples are finite.

---

# 37. Boundary reconstructed current samples

## 37.1 Cumulative or previous-aligned capacity

Derivative-based cumulative reconstruction and previous-aligned incremental reconstruction cannot determine the first sample of the entire dataset. The library MUST NOT fabricate a value.

Therefore:

```text
current_mA[0] = NaN
```

is the required endpoint result for these reconstruction paths, subject to Section 36.1.

## 37.2 Next-aligned incremental capacity

Next-aligned incremental reconstruction MUST set the final current sample of the entire dataset to `NaN`; its first sample MAY be finite. It MUST NOT impose an additional first-sample `NaN`.

## 37.3 Warnings and chunks

Unavailable endpoint values MUST trigger the standard missing-value warning. Endpoint rules apply to the entire logical dataset and MUST NOT be repeated at processing chunk boundaries. Next-aligned reconstruction MUST retain enough lookahead to use the first row of the following chunk.

---

# 38. Generic CSV and TXT reader

The generic delimited reader SHOULD require minimal manual configuration.

It SHOULD support automatic detection of:

```text
comma delimiter
semicolon delimiter
tab delimiter
whitespace delimiter
decimal point
decimal comma
header presence
common text encodings
```

Established third-party parsing libraries MAY be used when they improve correctness, maintainability, or performance.

## 38.1 Explicit parser overrides

Generic CSV/TXT APIs MUST provide explicit `sep`, `decimal`, `encoding`, `header`, and `skiprows` overrides. These options allow users to declare parsing structure when detection is ambiguous; their exact semantics are defined in the Architecture/API Specification.

---

# 39. CSV/TXT automatic inspection

Large text files SHOULD NOT need to be fully loaded in order to detect their structure.

The implementation MAY inspect a bounded initial sample in order to determine:

```text
encoding
delimiter
decimal separator
header presence
candidate column names
candidate units
```

The complete data shall subsequently be processed from the beginning.

Sampling MUST NOT cause rows to be silently lost.

---

# 40. Generic files without recognizable headers

If automatic recognition fails, explicit positional mapping MUST remain possible.

For example:

```python
read(
    "file.txt",
    columns={
        "time": 0,
        "current": 3,
        "voltage": 6,
    },
)
```

This makes headerless files valid inputs where the user knows the relevant column positions.

# 41. File-format detection

The primary reading interface SHOULD identify supported formats automatically.

Example:

```python
df = read("experiment.mpr")
```

Detection MAY use:

- file extension;
- magic bytes;
- known file signatures;
- textual structure;
- binary structural markers.

Where practical, content SHOULD be inspected rather than trusting the file extension alone.

An explicit reader override MAY be exposed for advanced use.

# 43. Vendor reader responsibilities

A vendor-specific reader SHOULD primarily be responsible for:

1. identifying the source format;
2. extracting potentially useful source columns;
3. providing known semantic information;
4. providing known unit information;
5. identifying format-specific special cases.

Generic functionality SHOULD handle:

- canonical naming;
- common unit conversion;
- validation;
- merging;
- exporting;
- generic recognition logic.

---

# 44. Standard read pipeline

A high-level read operation shall conceptually perform:

```text
SOURCE FILE
    │
    ▼
detect file format
    │
    ▼
select source reader
    │
    ▼
extract candidate information
    │
    ▼
column + unit recognition
    │
    ├───────────────┐
    │               │
    ▼               ▼
  time            voltage
    │               │
    └───────┬───────┘
            │
            ▼
   usable current available?
        │              │
       yes             no
        │              │
        │              ▼
        │      capacity recognition
        │              │
        │        semantics known?
        │          │          │
        │         yes         no
        │          │          │
        │          ▼          ▼
        │     reconstruct    error /
        │       current      explicit override
        │          │
        └──────────┴──────────
                   │
                   ▼
            unit normalization
                   │
                   ▼
             time origin = 0
                   │
                   ▼
                validation
                   │
                   ▼

        time_s      float64
        current_mA  float64
        voltage_V   float64
```

Internal implementation MAY reorder operations for efficiency provided the observable scientific result remains equivalent.

---

# 45. Public API philosophy

The public API SHOULD be predominantly function-oriented.

Ordinary users should not be required to interact with custom dataset wrapper classes.

The simplest expected usage is:

```python
df = read("experiment.mpr")
```

The result is a standard pandas DataFrame.

---

# 46. Expected high-level API

The library SHOULD eventually expose functions conceptually similar to:

```python
read(...)
iter_read(...)
detect_format(...)
merge(...)
convert(...)
write(...)
```

Exact names and signatures shall be defined in the Public API Specification.

---

# 47. `read()`

`read()` shall be the convenience interface for reading one complete dataset into memory.

Conceptually:

```python
df = read("experiment.mpr")
```

It should automatically perform:

- format detection;
- reading;
- column recognition;
- unit normalization;
- current acquisition;
- time normalization;
- validation.

For extremely large datasets, users SHOULD be encouraged to use streaming conversion or chunk-based APIs instead.

---

# 48. `iter_read()`

A chunk-oriented interface SHOULD be provided for formats that support incremental processing.

Conceptually:

```python
for chunk in iter_read("large_file.csv"):
    ...
```

Each yielded chunk MAY be a pandas DataFrame containing the canonical schema.

Scientific output MUST NOT depend on the chosen chunk size.

---

# 49. Large-file requirements

Source files and standardized outputs may be several gigabytes.

Memory usage is therefore a first-class engineering requirement.

The implementation SHOULD avoid unnecessary copies.

Where possible:

```text
read chunk
    ↓
standardize chunk
    ↓
write chunk
    ↓
discard chunk
    ↓
continue
```

shall be preferred over full-file materialization.

---

# 50. pandas and PyArrow

The public tabular interface SHALL remain pandas-based for v0.1.

This does not require pandas to be the only internal engine.

PyArrow MAY be used internally for:

- delimited-file reading;
- typed conversion;
- Parquet operations;
- chunked processing;
- reduced memory copying;
- efficient columnar operations.

The implementation strategy SHOULD be benchmark-driven.

---

# 51. Chunk-boundary state

Chunk processing MUST preserve sufficient information across boundaries to produce the same scientific result as continuous processing.

Depending on the operation, state may include:

```text
previous final time
previous final capacity
previous relevant auxiliary values
```

For example:

```text
chunk 1 final:
t = 100
Q = 5.0

chunk 2 first:
t = 101
Q = 5.1
```

Current reconstruction for the first row of chunk 2 shall use:

```text
Δt = 101 - 100
ΔQ = 5.1 - 5.0
```

The first row of every chunk MUST NOT receive an artificial `NaN`.

---

# 52. Chunk-size invariance

The result of processing a dataset MUST NOT depend on the chosen chunk size.

The following should therefore produce scientifically equivalent data:

```text
chunk size = 10,000 rows
chunk size = 100,000 rows
chunk size = 1,000,000 rows
non-chunked processing
```

This invariant MUST be tested.

---

# 53. Third-party reader limitations

Some proprietary-format libraries may internally load entire files into memory.

If a dependency prevents true streaming:

- the limitation MUST be documented;
- the library MUST NOT falsely claim streaming support for that format;
- other parts of the pipeline SHOULD remain memory-efficient where possible.

---

# 54. Direct conversion

The library SHOULD support direct standardized conversion without exposing the entire result in memory.

Conceptually:

```python
convert(
    "large_input.csv",
    "standardized.parquet",
)
```

The implementation should ideally perform:

```text
read
↓
standardize
↓
write
```

incrementally.

## 54.1 Successful streaming completion

Whole-dataset checks, including the existence of finite time and finite reconstructed current, MAY be deferred until the end of processing. `iter_read()` MAY therefore raise after yielding earlier chunks. `convert()` MUST write temporary output and publish the destination atomically only after successful completion; failed conversion MUST NOT publish a partial destination.

---

# 55. Missing values

Rows containing `NaN` values MUST NOT be automatically removed.

The library MUST emit a warning when canonical output contains missing values.

The warning SHOULD report:

- affected canonical columns;
- number of affected rows.

Example:

```text
Standardized dataset contains missing values:

current_mA: 1 row
voltage_V: 42 rows
```

The DataFrame shall still be returned unless the missing information makes safe processing impossible.

---

# 56. Internal validation

Validation is required even if no public `validate()` API is initially exposed.

Standardized data MUST be checked for:

- required canonical columns;
- required canonical column ordering;
- compatible numeric types;
- canonical units by construction;
- valid elapsed-time behavior;
- time monotonicity;
- missing values;
- reconstruction validity where applicable.

Validation MUST NOT silently modify the dataset.

---

# 57. Error and warning policy

Recoverable conditions SHOULD produce warnings.

Unsafe or impossible operations MUST produce exceptions.

Warnings are appropriate for cases such as:

```text
retained NaN values
recoverable malformed rows
non-critical source irregularities
capacity-derived first current value unavailable
```

Exceptions are appropriate for:

```text
unsupported format
missing time
missing voltage
missing current with no safe reconstruction path
ambiguous required columns
unknown required units
non-monotonic time
unsafe merge
unrecoverable corruption
```

---

# 58. Domain-specific exceptions

The project SHOULD define explicit exceptions such as:

```python
UnsupportedFormatError
MissingColumnError
AmbiguousColumnError
UnknownUnitError
CurrentReconstructionError
NonMonotonicTimeError
IncompatibleDataError
CorruptedFileError
```

Exception messages MUST be human-readable and actionable.

---

# 59. Corrupted and partially readable files

Where technically possible, the library SHOULD recover readable data from partially malformed input.

Any recovery MUST produce an appropriate warning.

The library MUST NOT silently skip large or scientifically meaningful portions of a file.

When safe interpretation is no longer possible, processing MUST stop.

---

# 60. Merge purpose

Multiple standardized datasets MAY be concatenated to represent sequential acquisitions of the same physical experiment.

Examples include:

- an acquisition interrupted and restarted;
- an instrument that creates multiple files;
- a cell transferred from one cycler to another;
- manually separated experimental segments.

Files may originate from different supported instruments.

Version 0.1 merging operates on canonical DataFrames. `convert_many()` and streaming merge-to-file are deferred beyond v0.1.

---

# 61. Merge ordering

The order of concatenation MUST be explicitly determined by the user.

The library MUST NOT reorder files automatically based on:

- filenames;
- timestamps;
- vendor metadata;
- creation dates.

If the user supplies:

```text
A
B
C
```

the logical order is:

```text
A → B → C
```

---

# 62. Merge schema

Since each dataset is standardized before merging, every merge input must provide:

```text
time_s
current_mA
voltage_V
```

No vendor-specific column reconciliation is required at merge time.

## 62.1 Merge input validation

Every input MUST satisfy complete canonical validation, including Section 10.1. An empty input collection or any empty input dataset MUST raise `IncompatibleDataError`. A collection containing one valid dataset MUST return a canonical copy of that dataset.

---

# 63. Merge time semantics

The first finite time of the first dataset is:

```text
time_s = 0
```

Each subsequent dataset shall retain its internal time intervals.

Only its absolute offset shall change.

---

# 64. Merge bridge interval

The first finite point of a subsequent dataset should occur one estimated sampling interval after the final finite point of the preceding dataset.

The preferred bridge interval is:

> The final valid positive sampling interval of the preceding dataset.

Example:

```text
A:
0
10
20
30

B:
0
5
10
15
```

The final valid interval of A is:

```text
10 s
```

Therefore B becomes:

```text
40
45
50
55
```

and the merged result is:

```text
0
10
20
30
40
45
50
55
```

The internal 5-second spacing of B remains unchanged.

---

# 65. Merge offset formula

For a subsequent dataset:

```text
offset =
    previous_last_finite_time
    + bridge_dt
    - next_first_finite_time
```

Then:

```text
new_next_time =
    original_next_time
    + offset
```

The endpoints MUST be the last finite time of the preceding dataset and the first finite time of the following dataset. Missing-time rows MUST remain present with `NaN` time after offsetting.

---

# 66. Merge interval selection

The preferred bridge interval shall be:

1. the final valid positive `dt` of the preceding dataset;
2. otherwise, the first valid positive `dt` of the following dataset.

Zero or negative intervals shall not be used as bridge intervals.

## 66.1 Adjacent-row bridge intervals

A candidate bridge interval MUST be the positive difference between finite times in adjacent original rows. Interval search MUST NOT span a missing-time row. Search the preceding dataset backwards first; if no valid interval exists, search the following dataset forwards.

For `A = [0, NaN, 10, 10]` and `B = [0, 5]`, A provides no valid positive adjacent-row interval. The bridge is therefore B's `5 s` interval, and the merged times are `[0, NaN, 10, 10, 15, 20]`.

---

# 67. Single-point merge inputs

If the preceding dataset contains only one usable time point, the bridge interval SHALL use the first valid positive interval from the following dataset.

Example:

```text
A:
0

B:
0
5
10
15
```

becomes:

```text
0
5
10
15
20
```

after appropriate offsetting of B.

---

# 68. No available bridge interval

If neither adjacent dataset provides a valid sampling interval, the library MUST NOT invent one.

The merge MUST fail.

This includes a situation where both adjacent datasets contain only one usable point.

---

# 69. Real-world acquisition gaps

Version 0.1 shall not attempt to reconstruct downtime between acquisitions.

If:

```text
measurement A ends at 10:00
measurement B begins at 12:00
```

the two-hour gap is intentionally ignored unless a future specification introduces an explicit feature for preserving such gaps.

Merged time therefore represents continuous experimental sequence time, not necessarily wall-clock time.

---

# 70. Cycles and merge behavior

Cycle information is intentionally irrelevant to v0.1 merging.

Cycles shall not be read, preserved, renumbered, or calculated by the standardization library.

Cycle calculation belongs entirely to the downstream analysis library after merging.

---

# 71. Output formats

Version 0.1 MUST support:

```text
Parquet
CSV
TXT
```

Excel output is deferred beyond v0.1.

## 71.1 Canonical text output

CSV/TXT output MUST use UTF-8 encoding, a decimal point, canonical column headers, and no index column. CSV MUST use a comma separator; TXT MUST use a tab separator. Custom destination dialects are deferred beyond v0.1.

---

# 72. Recommended output format

Apache Parquet SHALL be the recommended standardized interchange format.

Reasons include:

- preserved numeric types;
- compression;
- efficient storage;
- fast reads;
- efficient column selection;
- suitability for very large datasets;
- compatibility with pandas and PyArrow.

---

# 73. CSV output

CSV SHALL remain available for interoperability.

Users should be informed that large CSV files:

- occupy significantly more storage;
- parse more slowly;
- do not strongly preserve types;
- do not provide native metadata about numeric representation.

---

# 74. TXT output

Delimited TXT export MUST provide equivalent functionality to CSV using the canonical tab-separated dialect defined in Section 71.1.

---

# 75. Excel output

Excel output is deferred beyond v0.1. If introduced later, it MAY be supported as a convenience format.

Any future Excel implementation MUST NOT present the format as suitable for arbitrary dataset sizes.

That implementation MUST detect spreadsheet row limits.

It MUST fail clearly instead of truncating data silently.

---

# 76. Output consistency

Equivalent standardized data exported to different formats SHOULD preserve numerically equivalent values within the limitations of the destination format.

Parquet shall be considered the reference output when maximum fidelity is required.

---

# 77. Recognition subsystem architecture

Column and unit recognition SHALL be treated as a first-class module.

Conceptually:

```text
raw header
    │
    ▼
label normalization
    │
    ▼
quantity candidate generation
    │
    ▼
unit recognition
    │
    ▼
semantic classification
    │
    ▼
negative evidence
    │
    ▼
confidence / ambiguity resolution
```

Capacity recognition shall use the same infrastructure while exposing additional semantic classes.

---

# 78. Recognition result model

Internally, recognition SHOULD expose structured information rather than only returning a column name.

Conceptually:

```python
ColumnMatch(
    column="Discharge Capacity(mAh)",
    quantity="capacity",
    semantic="discharge_capacity",
    unit="mAh",
    confidence=...,
)
```

The exact data structure shall be defined in the Architecture/API Specification.

---

# 79. Recognition extensibility

Recognition rules SHOULD be data-driven wherever practical.

Adding a new known alias SHOULD preferably require editing a registry rather than modifying recognition algorithms.

This is particularly important because the alias database is expected to grow significantly over time.

---

# 80. Extending vendor support

Adding a new vendor SHOULD primarily require:

1. a format detector;
2. a reader;
3. vendor-specific aliases where required;
4. known field semantics;
5. unit mappings;
6. regression-test fixtures.

Canonical downstream code should remain unchanged.

# 102. Definition of success for v0.1

Version 0.1 can be considered functionally successful when supported source data from Bio-Logic, Neware, CSV, or TXT can reliably become:

```text
time_s      float64
current_mA  float64
voltage_V   float64
```

with the following guarantees:

- units are standardized;
- time starts at zero;
- source current sign is preserved;
- current is automatically detected where available;
- capacity-based current reconstruction occurs only when semantics are sufficiently known;
- automatic column recognition is powerful but conservative;
- explicit column overrides are available;
- explicit unit overrides are available;
- missing values are preserved and reported;
- non-monotonic time is rejected;
- sequential datasets can be merged in explicit user order;
- processing can operate incrementally where possible;
- Parquet output is available for efficient downstream use.

---

# 103. Scientific correctness criterion

A successful conversion is not merely one that produces three numerical columns.

It is one for which the library can justify that:

```text
time_s
```

represents elapsed time in seconds,

```text
current_mA
```

represents direct or safely reconstructed current in milliamperes,

and:

```text
voltage_V
```

represents measured electrochemical voltage in volts.

If this cannot be established safely, the operation should fail rather than generate misleading output.

---

# 104. Guiding statement

The project shall optimize for:

> **Predictability over cleverness, scientific correctness over convenience, and extensibility over vendor-specific shortcuts.**

Automatic recognition should make common cases effortless.

Explicit controls and clear errors should make uncommon cases safe.

The standardized output should be simple enough that downstream software no longer needs to know which instrument originally generated the data.
